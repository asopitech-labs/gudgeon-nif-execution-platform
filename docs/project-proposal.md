# GUDGEON 企画書

**GUDGEON — Gudgeon Unified Debuggable Guest Execution Orchestrator for NIF**

- Repository: `asopitech-labs/gudgeon-nif-execution-platform`

## 1. 概要

GUDGEONは、NIF（Nimony Intermediate Format）で表現されたプログラムを、単一の実行モデルのもとで解釈実行・ネイティブコンパイル・デバッグ・計測・ネイティブ相互運用できる実行プラットフォームである。

一般的なコンパイラ基盤では、IRはネイティブコードを生成するための一時的な表現として扱われる。GUDGEONでは、lowered program IRそのものを実行可能かつ観測可能な資産として扱う。同じプログラムモデルをVMで即時実行し、AOTでネイティブ化し、デバッガで停止・検査し、プロファイラやトレーサで計測できることを中核価値とする。

> Interpreted. Native. Observable.

## 2. 背景と課題

- IRの意味論を確認するために、毎回ネイティブコンパイルまで進める必要がある。
- コンパイラ、VM、デバッガ、計測系が別々の実行モデルを持つと、挙動差が発生しやすい。
- ソース位置、型、呼び出し履歴、値などのデバッグ情報が変換過程で失われやすい。
- ネイティブ関数の呼び出しと、ネイティブ側からNIFプログラムを呼ぶ経路が統一されていない。
- 新しい最適化やバックエンドを検証するための再現性の高い基準実装が不足しやすい。

GUDGEONは、NIFを中心に実行・変換・観測の境界を揃えることで、これらの問題を解消する。

## 3. ビジョンと設計原則

GUDGEONのビジョンは、NIFプログラムに対して「まず動かす」「正しく調べる」「速くする」「外部とつなぐ」を一貫した手順で実現することである。

1. **One semantic model** — VMとネイティブコード生成で同じ意味論を共有する。
2. **Debuggability by design** — デバッグ情報をIRの読み込みから実行まで保持する。
3. **Observability as a first-class feature** — トレース、プロファイル、カバレッジ、イベントフックを標準機能とする。
4. **Native interoperability** — NIFとネイティブの双方向呼び出しを明示的なABIで支える。
5. **Incremental delivery** — 最小VMから始め、検証可能な単位で機能を追加する。
6. **Deterministic behavior** — テストとデバッグに必要な再現性を優先する。

## 4. 目標

- NIFの読み込み、検証、正規化、実行を行う基盤を提供する。
- 参照実装となるインタープリタ／VMを構築する。
- 同一IRからネイティブコードを生成し、VMとの意味論的一致を検証する。
- ブレークポイント、ステップ実行、スタック、変数、式評価を含むデバッグ機能を提供する。
- DAP（Debug Adapter Protocol）により既存エディタから利用できるようにする。
- プロファイル、トレース、カバレッジなどの計測機能を提供する。
- 安全で明示的なFFIと埋め込みAPIを提供する。
- 実行経路間の差分を検出する適合性テスト群を整備する。

### 初期段階の非目標

- NimまたはNimonyコンパイラ全体の置き換え。
- あらゆるCPU、OS、ABIへの同時対応。
- 高度なJIT最適化の早期実装。
- 言語サーバ、パッケージマネージャ、IDEの独自再実装。
- VMとネイティブ実行の性能を最初から同等にすること。

## 5. 想定利用者とユースケース

### 想定利用者

- Nimony／NIFの実装者とコントリビュータ
- コンパイラ、ランタイム、デバッガの研究開発者
- Nim系ツールチェーンの拡張を行う開発者
- NIFプログラムを組み込みたいネイティブアプリケーション開発者
- 実行トレースやカバレッジを必要とする解析ツール開発者

### 主なユースケース

- NIFファイルをその場で実行し、意味論を確認する。
- VM実行とネイティブ実行の結果を比較する。
- エディタからNIF由来のプログラムをデバッグする。
- 命令、関数、割り当て、外部呼び出しのイベントを記録する。
- NIFからネイティブライブラリを呼び出す。
- ネイティブアプリケーションにGUDGEONを埋め込む。
- 最適化パスの前後で振る舞いが変化していないことを検証する。

## 6. 製品スコープ

### NIF Frontend

入力の読み込みとバージョン識別、構文・型・参照整合性の検証、ソース位置の保持、実行用内部表現への正規化、未対応機能の診断を行う。

### Execution VM

関数呼び出し、制御フロー、値、メモリを扱う参照実装を提供する。決定的なステップ実行、構造化された失敗、キャンセル、タイムアウト、状態スナップショットを支える。

### Native Compilation

共通Execution IRからネイティブコードを生成するAOT経路を提供する。型、呼び出し規約、デバッグ情報をVMと共有し、differential testingで適合性を検証する。

### Debugging

行／命令／関数ブレークポイント、step in／over／out、continue、pause、スタック、変数、式評価、失敗時停止、DAP接続を提供する。

### Instrumentation

命令、基本ブロック、関数、外部呼び出しのイベント、プロファイル、トレース、カバレッジ、利用者定義フックを提供する。

### Native Interoperability

NIFからネイティブ関数を呼ぶFFIと、ネイティブ側からNIF関数を呼ぶ埋め込みAPIを提供する。型変換、所有権、ライフタイム、エラー、コールバック、再入性の契約を明文化する。

## 7. アーキテクチャ案

1. **Loader** — NIF入力とバージョンを読み込む。
2. **Verifier** — 型、参照、制御フロー、ABI条件を検証する。
3. **Execution IR** — VM、ネイティブ生成、デバッグ、計測が共有する正規化表現。
4. **Runtime Services** — メモリ、失敗、外部シンボル、スケジューリング、ホストAPIを提供する。
5. **VM Backend** — 参照意味論として解釈実行する。
6. **Native Backend** — 同じExecution IRをネイティブコードへ変換する。
7. **Debug Service** — 実行制御、状態検査、ソースマッピング、DAPを提供する。
8. **Instrumentation Service** — イベント、プロファイル、トレース、カバレッジを提供する。
9. **Embedding API / CLI** — ツールおよびホストアプリケーション向けの利用面を提供する。

VMとNative BackendはRuntime ServicesとExecution IRの契約を共有する。デバッグと計測は共通のイベントおよび状態モデルを介して接続する。

## 8. 開発計画

### Phase 0 — Foundations

対象NIFサブセット、Execution IR、値モデル、リポジトリ構成、CI、テスト規約、診断形式、fixtureを定義する。

**完了条件:** 最小入力を読み込み、検証結果を安定した形式で出力できる。

### Phase 1 — VM MVP

整数、真偽値、基本制御フロー、関数呼び出し、CLI、決定的な実行テストを実装する。

**完了条件:** 代表的な小規模プログラムをVMで再現可能に実行できる。

### Phase 2 — Debugging and Instrumentation

停止、ステップ、スタック／変数参照、DAP最小機能、関数／命令イベント、プロファイル、カバレッジを実装する。

**完了条件:** エディタから代表プログラムをデバッグし、実行トレースを取得できる。

### Phase 3 — Native Compilation

Execution IRからネイティブコードを生成し、VMとの適合性テスト、ソースマッピング、ネイティブデバッグ情報を追加する。

**完了条件:** 対応サブセットについてVMとネイティブ実行が同じ観測結果を返す。

### Phase 4 — Native Interoperability and Hardening

FFIと埋め込みAPIを安定化し、所有権、失敗、コールバック、再入性、性能、セキュリティ、互換性を改善する。

**完了条件:** ネイティブホストとNIFプログラムが双方向に呼び出せ、公開APIの互換性方針が定義されている。

## 9. 成果物

- GUDGEON CLI、NIF loader／verifier、Execution IR仕様、参照VM
- Native Backend、DAP adapter、Instrumentation API
- FFI／Embedding API、Conformance test suite
- サンプル、統合例、アーキテクチャ／ABI／デバッグ／運用文書

## 10. 品質戦略

単体、fixture、differential、property-based、fuzzing、integrationの各テストを組み合わせる。起動時間、実行時間、メモリ、計測オーバーヘッドを継続測定する。VMとネイティブ実行の結果だけでなく、観測イベントも比較する。

## 11. 成功指標

- 定義したNIFサブセットの命令／型カバレッジ
- VMとネイティブ実行の適合テスト合格率
- ソース位置と原因を含む診断の割合
- DAP主要シナリオの成功率
- 計測無効時／有効時のオーバーヘッド
- クラッシュ、未定義動作、非決定的失敗の件数
- 外部プロジェクトでの統合成功数

数値目標はPhase 0でベースラインを取得した後に固定する。

## 12. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| NIF仕様の変化 | loaderとIRの互換性が崩れる | 入力バージョンを識別し、変換層を分離する |
| VMとnativeの意味論差 | 正しさへの信頼を失う | 共通Execution IRとdifferential testを採用する |
| デバッグ情報の欠落 | 実用的なデバッグが困難 | ソース位置と型情報を初期段階から保持する |
| FFIの所有権不整合 | クラッシュやリークを招く | ABI、所有権、エラー境界を文書とテストで固定する |
| スコープ過大 | MVP到達が遅れる | NIFサブセットとPhaseごとの完了条件を明示する |
| 計測オーバーヘッド | 本番利用を妨げる | 無効時の高速経路と段階的な計測レベルを設ける |

## 14. 初期バックログ

1. 対象NIFバージョンと最小サブセットを確定する。
2. NIF fixtureの収集方法とライセンス条件を決める。
3. 値、型、関数、制御フローのExecution IRを定義する。
4. loader／verifierの診断形式を定義する。
5. VMの最小命令セットと実行ループを実装する。
6. VMと期待結果を比較するconformance harnessを作る。
7. デバッグイベントと計測イベントの共通モデルを設計する。
8. DAP MVPの対応リクエストを決める。
9. Native Backend候補の最小PoCを評価する。
10. FFI／Embedding APIの所有権モデルを設計する。
11. CI対象プラットフォームとサポート方針を決める。
12. セキュリティ境界と非信頼NIFの扱いを文書化する。

## 15. 検討事項

- 最初に固定するNIFバージョンと命令サブセット
- NIFからExecution IRへ正規化する境界
- Native Backendの第一候補
- VMとネイティブ間のGC、参照、所有権モデル
- 非同期処理、スレッド、例外を扱うPhase
- DAP上でNim、NIF、生成コードを対応付ける方法
- 計測イベントの安定性と外部互換性
- 非信頼入力を実行する場合の隔離方式

## 16. 最初の公開リリースの定義

- 対応NIFサブセットが文書化されている。
- 代表プログラムをVMで実行できる。
- エラーが構造化され、入力位置と原因を確認できる。
- 最小限のデバッグと実行トレースが利用できる。
- VMとNative Backendの適合性を示す自動テストがある。
- CLIまたは埋め込みAPIの利用例が再現できる。
- ライセンス、セキュリティ、互換性、コントリビューション方針が公開されている。

## 17. 結論

GUDGEONは、NIFを単なる中間生成物ではなく、実行・検証・観測・統合の中心に据える。VM、ネイティブコンパイル、デバッグ、計測、FFIを共通モデルの上に構築することで、Nimony周辺の実験速度と正しさの両方を高める。

この企画書は実装の進展と設計判断に合わせて更新し、各変更をGit履歴として残す。
