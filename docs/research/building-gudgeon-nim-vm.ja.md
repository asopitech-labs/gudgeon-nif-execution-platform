# GUDGEON構築：Nim VMと実行プラットフォーム

## エグゼクティブサマリー

Nimが生成するCコードは、人間が読んだり保守したりすることを意図したソースコードとしてではなく、コンパイラのバックエンドが生成する中間成果物として評価されるべきである。　見冗長に見える点、一時変数、キャスト、ランタイム呼び出し、防御的な初期化処理などは、多くの場合、言語セマンティクスを表現するため、あるいは後段のCコンパイラが最適化を行うための入力を提供するためのものである。これら自体は、実行コードの品質が低いことの証拠にはならない。

より重要なエンジニアリング上の知見はアーキテクチャに関するものである。従来のC/C++/JavaScriptエミッターは、歴史的にターゲットコードを文字列やロープ（rope）として直接出力してきた。Nimのコンパイラ開発に関する議論の中では、これはコード生成後の最適化を制限し、一部のバグを修正しにくくするレガシー設計であると指摘されている。NIF/Nimony/NIFCという方向性は、この境界を明示的な中間表現と段階的なローワリング（lowering）に置き換えるものである。

GUDGEONにとって、この知見は設計上の選択を明確にする。すなわち、生成されたCコードを共通の実行コントラクトとして扱うべきではない。代わりに、ローワリング済みの実行可能なIR（中間表現）と、ソース・型・所有権・FFIに関するメタデータを共通のコントラクトとして扱うべきである。VMはこの表現を解釈でき、ネイティブバックエンドはこれをC、LLVM、あるいは直接機械語へとローワリングできる。デバッグや計測（instrumentation）は、いずれのモードにおいてもソースを意識した形を維持できる。

## 「生成されたCコードの品質」が意味すること

「品質」には、いくつかの独立した側面がある。

| 側面 | 実際の評価 |
|---|---|
| 可読性・手作業での保守性 | 設計上、低い。生成されたCはユーザー向けのソース言語ではない。 |
| Cへのマッピングの正確性 | 成熟しているが、通常のバックエンドおよびABIのバグの影響は受けうる。 |
| 最適化器との親和性 | 最終的な最適化作業をGCCやClangが担うため、多くの場合良好。 |
| 最終的なバイナリの性能とサイズ | Cに近い水準になりうるが、ランタイム機能・安全性チェック・最適化フラグ・LTO・対象プログラムに依存する。 |
| デバッグ体験 | ソースネイティブなデバッグより劣る。生成された名前・一時変数・ローワリングされた制御フローに直面する可能性がある。 |
| バックエンドアーキテクチャ | 従来の直接出力モデルは既知の限界であり、NIF/NIFCはこれを構造的に解決する。 |

したがって、生成されたCファイルが大きいからといって実行バイナリが大きくなるとは限らず、見た目がぎこちないCコードだからといって最適化器がそのぎこちない構造をそのまま残すとは限らない。逆に、良好なベンチマーク結果が出たからといって、あらゆる生成プログラムがクリーンなローワリングや理想的なデバッグ体験を持つことが保証されるわけでもない。

## C出力が読みにくい理由

Nimは、Cを出力する前後で、より高レベルな言語機能を明示的なランタイム操作および制御フロー操作へとローワリングする。生成されたコードには、次のような詳細が現れることがある。

- 一時的な値と初期化処理
- 文字列およびシーケンスの表現
- 境界チェック、オーバーフローチェック、nilチェック
- 型情報とランタイムヘルパー
- ARC/ORCによるコピー・ムーブ・破棄操作
- 例外処理・エラー処理のパス
- 名前マングリングとモジュールレベルのリンケージ

これはコンパイラの挙動を示す貴重な証拠である。ソースレベルの構文がどのようにデータレイアウト、呼び出し、分岐、所有権操作へと変換れるかを示している。しかし、元のプログラムを理解したいユーザーにとって適切な抽象化ではない。

ここで問うべきなのは「これはきれいなCコードに見えるか」ではなく、「このローワリングはNimのセマンティクスを保持しているか、意図したABIを明示しているか、そしてCコンパイラが効果的に最適化できるだけの構造を残しているか」である。

## 直接的なC出力の限界

Nimのコンパイラ開発に関する議論では、従来のC/C++/JavaScriptコード生成器が文字列やロープを直接生成していると説明されている。このアプローチ自体は機能するが、構造的なコストを伴う。一度コードがテキストとして出力されてしまうと、コンパイラはその上で原理的な変換や解析を行うためのターゲット言語表現もはや持たなくなる。

この帰結は単なる見た目の問題にとどまらない。構造化されたバックエンドIRは、次のことを可能にする。

- レンダリング前のターゲット固有の変換
- 宣言・リンケージ・制御フローのより明確な取り扱い
- 正確性についてのより局所的な推論
- 壊れにくいソースコード生成
- 複数ターゲットへのよりクリーンな対応経路

これはGUDGEONにとって重要な区別である。Cのテキストは出力形式の一つに過ぎない。それがシステムの主要な意味的インターフェースになるべきではない。

## NIF、Nimony、NIFC

NIFは、ソースの位置情報を保持しながら、異なる抽象度のレベルの表現を運ぶことができる、汎用的なコンパイラ構築用フォーマットとして設計されている。Nimonyとそのローワリング処理系は、この段階的なモデルを用いて、パース・意味解析・変換を分離している。

文書化されているローワリングの流れには、次のような操作が含まれる。

- イテレータのインライン化
- ラムダリフティング
- ポインタの参照解決および参照渡しの挿入
- コピー／複製（dup）操作の挿入
- 制御フロー式の文への変換
- デストラクタの挿入
- 組み込み処理からランタイム操作へのマッピング
- 例外処理の変換

NIFCは、C自体では扱いにくい、あるいは曖昧になりがちなコンパイラを難しくを目的とした、C近縁の方言である。例えば、値の配列、その一要素へのポインタ、配列全体へのポインタを区別することが挙げられる。また、継承や例外処理のような構文についても、バックエンドが必要とする情報を早期に失うことなくモデル化する。

実務上の含意として、最も強固な実行境界は、Nimの高レベルな機能がローワリングされた後、かつ情報がCテキストへと平坦化される前の段階にあるということになる。

## デバッグと来歴（provenance）

生成されたCコードのデバッグは、通常いくつもの変換を経由する。

```
Nimソースコード
  -> ローワリング済み表現
  -> 生成されたCコード
  -> DWARFまたはCodeView
  -> マシン上の位置情報
  -> デバッガ
```

このワークフロー自体は機能するが、ソースレベルのNimの値やフレームを確実に再構築することを難しくする。デバッガが目にするのは、名前マングリング、一時変数の導入、ネイティブなローワリングを経た後の世界である。

NIFのインライン行情報とNimonyの方向性は、より良い基盤を提供する。ローワリング済みの実行表現は、少なくとも次の情報を保持できる。

- ソースファイル、行、列
- ソースシンボルの識別情報
- Nimの型の識別情報とレイアウト
- スコープおよびフレーム情報
- 文、呼び出し、割り当て、書き込みなどの意味的タグ
- 所有権とライフタイムに関する操作
- FFI記述子

GUDGEONにおいては、これらはコード生成後に付加されるオプションの注釈ではなく、ランタイムのファーストクラスなメタデータとして扱われるべきである。

## GUDGEONへの示唆

### 1. 共有コントラクトとしてローワリング済みの実行IRを用いる

GUDGEONは、ローワリングされたNIF/Final-IR層を読み込み、内部の実行IR（Execution IR）へと正規化すべきである。Cでもなく、VM固有のバイトコードでもない、そのIRこそが以下の要素間で共有される境界であるべきだ。

```
実行IR
├─ VMインタプリタ
├─ C/NIFCバックエンド
├─ LLVMバックエンド
└─ 将来の直接コード生成／JITバックエンド
```

専用の内部表現を持つことで、GUDGEONは上流のフォーマット変更から切り離される一方、別個のスタックベースのバイトコード言語への不要な早期変換も回避できる。

### 2. フレーム／レジスタ型インタプリタモデルを優先する

可変ストレージを伴うローワリング済み表現は、フレーム、ローカル変数、引数、一時変数、プログラムカウンタへと自然にマッピングされる。これをまずスタックバイトコードへ変換すると、意味的な変換がもう一段階加わることになり、ソースレベルでの検査が間接的になりかねない。

VMは、自身のデバッグモデルと同じ用語でフレームと値を公開すべきである。

```
フレーム
├─ 関数とソース範囲
├─ プログラムカウンタ
├─ 引数
├─ ローカル変数と一時変数
└─ 戻り値と例外状態
```

### 3. ライフタイムのセマンティクスを明示的に保つ

GUDGEONは、ローワリングされたARC/ORCの挙動を、それとは無関係なVM専用のガベージコレクタに置き換えるべきではない。ローワリング処理系がコピー・ムーブ・破棄の各操作を明示的にしている場合、VMとネイティブバックエンドは同じ所有権コントラクトを実行すべきである。これにより、インタプリタ実行とネイティブ実行の間の意味的な乖離を減らすことができる。

### 4. FFIを実行モデルの一部として扱う

CのABI呼び出しは、通常のNimの相互運用性において中心的な役割を果たす。実行表現は、各外部呼び出しについて、ライブラリ、シンボル、呼び出し規約、引数と戻り値の型、所有権規則、エラー規約を含む記述子を保持すべきである。

```
外部関数（ForeignFunction）
├─ ライブラリとシンボル
├─ 呼び出し規約
├─ パラメータと戻り値の型
├─ 所有権規則
└─ エラー規約
```

ネイティブコードは直接リンクまたは呼び出しを行うことができ、VMはFFIブリッジを利用できる。いずれのモードも同一の記述子を消費すべきである。

ポインタについても明示的なモデルが必要である。システムプログラミング言語向けのVMは、すべてのポインタが管理されたヒープ参照であると仮定することはできない。GUDGEONは、VMヒープ上のポインタとFFI経由で受け取るネイティブポインタとを区別しつつ、安全性と所有権の規則を可視化すべきである。

### 5. 計測（instrumentation）をエンジンに依存しない形にする

計測は、デバッガ専用のVMフックの集合ではなく、共有されるイベント層であるべきである。有用なイベントの種類には、文の開始と終了、呼び出し、読み取り、書き込み、割り当て、解放、例外送出、例外捕捉などが含まれる。

これにより、同一の実行モデルで次のことをサポートできるようになる。

- ソースレベルのデバッグ
- プロファイリング
- トレーシング
- カバレッジ計測
- 記録と逆方向デバッグ（reverse-debugging）の実験

### 6. VMとネイティブ実行に単一のデバッグモデルを用いる

公開されるデバッグコントラクトは、ソースの位置情報、シンボル、型、値、フレーム、スコープ、スレッド、ブレークポイント、実行状態をモデル化すべきである。VMバックエンドは自身の内部状態からこれらに応答できる。ネイティブバックエンドは、同じメタデータをネイティブのデバッグ情報へとマッピングし、可能な限りDWARFやCodeViewから値を再構築できる。

DAP（Debug Adapter Protocol）は、外部プロトコルの境界として適切な選択である。これにより、GUDGEONはランタイム設計を特定のIDEに結び付けることなく、既存のエディタと統合できる。

## 推奨される検証作業

この設計は、同一のローワリング済みプログラムに対してVM実行とネイティブ実行を比較する、小規模な適合性検証コーパスによってテストされるべきである。このコーパスは、次の項目をカバーすべきである。

- プリミティブな算術演算と制御フロー
- オブジェクト、文字列、シーケンス
- ローワリング後のクロージャとイテレータ
- ARC/ORCのコピー・ムーブ・破棄のパス
- 例外処理
- importc、dynlib、呼び出し規約、ポインタの往復
- ソースブレークポイント、ステップ実行、スタックトレース、ローカル値の検査

最初の意味のあるマイルストーンは、単に「Hello, world.」を実行することではない。ソースから可視な状態を持つプログラムを実行し、VM・デバッガ・ネイティブ実行経路のいずれもが観測可能な挙動において一致することを証明することである。
